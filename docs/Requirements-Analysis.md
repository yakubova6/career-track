
Выявление и анализ требований  

---

**Выявление требований** — это процесс поиска, сбора и уточнения потребностей заказчиков и пользователей для создания правильного продукта. Ошибка на этом этапе обходится в десятки раз дороже, чем плохая архитектура или баг в реализации.

В рамках проекта «Интерактивный конструктор карьерного трека» проведён анализ требований на основе:
- концепции проекта (Vision & Scope);
- анализа предметной области
- анализа конкурентов (Яндекс Карьерный навигатор, hh Карьера, LinkedIn Career Explorer, O*NET);
- целевой аудитории (студенты, начинающие специалисты, меняющие профессию).

**Основной метод выявления требований:** исследование рынка + анализ конкурентов + интервью с потенциальными пользователями.

## 2. Стейкхолдеры и акторы

Согласно лекции, важно разграничивать **стейкхолдеров** (кому важна система) и **акторов** (кто взаимодействует с системой напрямую).

### 2.1. Стейкхолдеры

| Стейкхолдер | Интерес | Влияние |
|-------------|---------|---------|
| **Студент / начинающий специалист** | Получить понятный план развития навыков | Высокое (основной пользователь) |
| **Преподаватель / куратор** | Использовать систему для сопровождения студентов | Среднее |
| **Владелец продукта (команда проекта)** | Успешная защита проекта, Product-Market Fit | Высокое |
| **Владельцы API вакансий (hh.ru, Habr Career)** | Корректное использование данных | Среднее |
| **Образовательные платформы (Stepik, Coursera)** | Интеграция с треками | Низкое (потенциальное) |

### 2.2. Акторы

| Актор | Цель | Тип |
|-------|------|-----|
| **Студент** | Выбрать цель, указать навыки, получить карьерный трек | Человек |
| **Администратор** | Управлять справочниками профессий, навыков, категорий | Человек |
| **API вакансий** | Предоставить данные о вакансиях | Внешняя система |
| **Система аутентификации** | Подтвердить личность пользователя | Внешняя система |

## 3. Функциональные требования

Функциональные требования

| FR-2 | Система должна позволять пользователю авторизоваться и выходить из аккаунта. | Высокий |
| FR-3 | Система должна позволять пользователю указать карьерную цель (профессию и уровень). | Высокий |

| FR-5 | Система должна позволять пользователю редактировать и удалять навыки из профиля. | Средний |

| FR-7 | Система должна хранить историю изменений профиля. | Низкий |

### 3.2. Модуль «Анализ рынка труда»

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-8 | Система должна получать данные о вакансиях через внешний API. | Высокий |
| FR-9 | Система должна фильтровать вакансии по профессии, уровню и региону. | Высокий |
| FR-10 | Система должна извлекать требования (навыки) из текста вакансий. | Высокий |
| FR-11 | Система должна нормализовать навыки (приводить к единому справочнику). | Высокий |

| FR-20 | Система должна отображать Skill Gap в табличном виде. | Средний |
| FR-21 | Система должна обновлять Skill Gap при изменении профиля пользователя. | Средний |

### 3.4. Модуль «Построение карьерного трека»

## 4. Нефункциональные требования

Нефункциональные требования описывают, **как система должна работать**.

### 4.1. Производительность

| ID | Требование |
|----|------------|
| NFR-1 | Время отклика API — не более 2 секунд при 95% запросов. |
| NFR-2 | Построение карьерного трека — не более 5 секунд. |
| NFR-3 | Система должна выдерживать 1000 одновременных пользователей. |

### 4.2. Надёжность

| ID | Требование |
|----|------------|
| NFR-4 | Доступность системы — не менее 99% времени. |
| NFR-5 | Система должна корректно обрабатывать недоступность API вакансий. |
| NFR-6 | Резервное копирование данных — ежедневно. |

### 4.3. Безопасность

| ID | Требование |
|----|------------|
| NFR-7 | Пароли хранятся в хешированном виде (bcrypt/argon2). |
| NFR-8 | Аутентификация через JWT или сессии. |
| NFR-9 | Защита от SQL-инъекций и XSS. |
| NFR-10 | Персональные данные пользователей не передаются третьим лицам. |

### 4.4. Удобство использования

| ID | Требование |
|----|------------|
| NFR-11 | Интерфейс должен быть адаптивным (мобильные + десктоп). |
| NFR-12 | Время освоения интерфейса новым пользователем — не более 10 минут. |
| NFR-13 | Визуализация трека должна быть понятной без обучения. |

### 4.5. Сопровождаемость

| ID | Требование |
|----|------------|
| NFR-14 | Код должен быть покрыт тестами не менее чем на 70%. |
| NFR-15 | Документация API — в формате OpenAPI/Swagger. |
| NFR-16 | Архитектура должна позволять замену внешнего API без переписывания ядра. |

### 4.6. Ограничения

| ID | Требование |
|----|------------|
| NFR-17 | Система работает только с профессиями, по которым есть достаточно вакансий. |
| NFR-18 | Данные о вакансиях зависят от внешнего API. |
| NFR-19 | Уровень владения навыком субъективен (оценка пользователя). |

## 5. User Stories

**User Story** — это краткое описание функции с точки зрения пользователя.

### 5.1. Для студента

| ID | User Story | Приоритет |
|----|------------|-----------|
| US-1 | Как студент, я хочу создать профиль, чтобы система знала мои данные. | Высокий |
| US-2 | Как студент, я хочу указать карьерную цель, чтобы получить релевантный трек. | Высокий |
| US-3 | Как студент, я хочу добавить свои навыки, чтобы система оценила мой уровень. | Высокий |
| US-4 | Как студент, я хочу увидеть Skill Gap, чтобы понять, чего мне не хватает. | Высокий |
| US-5 | Как студент, я хочу получить карьерный трек, чтобы знать, что изучать и в каком порядке. | Высокий |
| US-6 | Как студент, я хочу видеть визуализацию трека, чтобы понимать свой прогресс. | Средний |

| ID | User Story | Приоритет |
